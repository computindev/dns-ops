02 — CURRENT TOKEN SYSTEM

De-facto, not designed

No formal token layer exists. The app runs on Tailwind's default palette with blue as the de-facto primary, gray neutrals, and a split warning hue (amber for authoritative-UNKNOWN, yellow for no-data) that should be consolidated.

Primary · blue (action, focus, links)

50 → 900. blue-600 = default button, blue-700 = hover, blue-500 = focus ring / icons.

Neutral · gray (text, borders, surfaces)

Most-used: gray-500 (meta), gray-900 (headings), gray-200 (borders). gray-400 = disabled.

Semantic · success / danger

Success emerald/green also doubles as a secondary brand accent on the home page. Danger red for errors & validation.

Warning · ⚠ split (consolidate to amber)

Amber (authoritative UNKNOWN) and yellow (no-data) are two overlapping warning scales. design-tokens.css merges them into one.

05 — PRIORITIES

What to design next

1

Cases / Signals workspace. The full signal→case→disposition→reopen→audit lifecycle is built in the API & DB with no operator UI. Biggest functional gap.

2

Consolidate the token system. Adopt design-tokens.css, unify the amber/yellow warning split, define success-vs-brand green, add dark-mode.

3

Admin / ops console. Ruleset activation + migrate/schema health (/api/health/detailed) have no surface.

4

Baseline-acceptance flow. TLS / SPF operational baselines can be accepted via API, not from the UI.

5

Open decisions: signup page, shadow-comparison view, legacy-tools panel, provider-template editor — keep API-only or add UI.
